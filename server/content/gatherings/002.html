01Cursor 里迭代尽调 Skill

廖律延续上期已开源的报告 Skill，上午刚测过一版，把它放进 Cursor 再讲一遍。目的没变：按律所写医疗报告／尽调报告的体例，生成格式可控的 Word，同时给模型留一点内容上的自主空间。

为什么换到 Cursor 里管

  • Skill、MCP、插件能在侧边栏列表里看摘要，比纯翻文件夹清楚。
  • 点开一条就能预览基本内容，也能跳到本机文件浏览器。
  • 迭代后除了原来那几个说明文件，脚本和示例也收进同一个 Skill。

内容与格式拆开

  • 现场演示只测转换格式，前端调研几乎没加约束，用「一句话」也能跑通链路。
  • 真正交付时可以把两条 Skill 串起来：一条管调研与内容定稿，一条管排版交付。
  • 上市公司公开信息多，模型能找到的材料也更熟；内容质量仍取决于你给的前端要求。

02Markdown 到 Word 的交付链

底层仍走 pandoc 命令行。模型的自主性主要用在「先爬信息、写成 Markdown」这一段；后面的转换尽量少让它自由发挥。

三步路径

  1. Markdown：调研结果先落成 .md（过程文件里还能看到 source）。
  2. HTML 中转：再转 Word。现场结论是：pandoc 原生映射对目录、合并单元格表格不够好，先走 HTML，Word 才能把表格解析成想要的样子。写 md 时也要照顾后续转换。
  3. 进文档改 XML：pandoc 调不了表格间距和列宽。框架已经搭好之后再改内部 XML，比一上来就改 Word 省很多 token。Skill 里用 Python 脚本做这一步；也可以换成 Office CLI 或在 Word 里手工收，只要接在 pandoc 成品之上即可。

reference.docx

  • 样式不靠改正文里的字体，而靠改 Word 样式；reference 就是这些样式的载体，Markdown 按 pandoc 规则映射上去。
  • 公司有模板或书面要求，可以直接让模型按 pandoc 映射规则去改 reference，不必自己从零点样式。
  • 目录页码偶发不准，在 Word 里更新域即可。

表格：什么时候成表、列宽怎么好看

  • md 本身只擅长最朴素的表。合并、复杂表要等到转 HTML 之后。
  • 「该不该做成表」这一段演示里没加约束，由模型在 md 阶段自己判断——也会出现不该成表的成了表、该成表的写成了段落。
  • 列宽：现场不是套 Word「根据内容调整」，而是让模型写一套「智能调整」并回写进 Skill；具体规则廖律会后再拆。
  • 可再收紧一条排版目标：单元格尽量不换行，整表换行次数最少。
会后动作：迭代版 Skill 会后开源，欢迎直接 PR。演示用长鑫公开信息起草，律师审过内容后，格式已接近可给客户的状态。

03Cursor 的云端、自动化与局部编辑

现场体感（国内）

  • 廖律实测：Cursor 里用模型不必单独翻墙，这是相对其他工具的明显优势。
  • 用得最多的是 Grok 4.6；也可以加 Kimi K3、自备 API Key。有人遇到过 Opus 等按地区拦截，即便把地址指到美国仍不可用，感觉 IP 核查偏严。
  • Pro 档另有约 20 美元／月的其他模型额度。Grok 的量用下来觉得大，Web Search 能通。

云端 Agent 与手机

  • 装了 Cursor 移动端，和电脑上的 Agent／任务实时同步；云朵标记的是 Cloud Agent。
  • 默认可上云，也可关掉。电脑关机后，云上的任务还能继续跑。

Automations

  • 例：每天 8:00 往 Slack 推一条「大湾区活动」盯盘。Slack MCP 接上之后，打开 Slack 就能看，类似「美版钉钉」。
  • 盯盘完整度一般，功能还没打磨；模型和已接的 MCP 都能在 Automation 里选。

部署与局部编辑

  • 站点放在 Cloudflare：对话改完，凭 API Key 自动部署；GitHub 与 Cloudflare 同步。别的 Agent 也能做，只是收进 Cursor。
  • Cursor 出身是 IDE：改一段 md／html／协议，切到 IDE 界面，选中再聊，只动这一段。纯 Agent 窗口做局部编辑很费劲。
  • Codex 右侧也能预览／改文件，工具在趋同。选中后旁边的 Quick Edit 或 Chat 都能改，和早期 VS Code 插件一个路数。Word 本身这套界面里还打不开。

仍未解决

  • 境外 Agent 的网页搜索，对境内站点覆盖偏弱。
  • 大量境内信息实际在微信里，Web Search 搜不到。上期讨论过，这期仍无干净方案。
  • WorkBuddy 对微信更友好；有人试过用混元补，不行。

04从超级个体到超级团队

阿欣从 WorkBuddy 新出的资料库／共建文件夹说起：律师团队里常有「下面还有小朋友」，怎样让 AI 在协作里磨合各人的偏好，而不是每人从零高压起步。

先成为超级个体

  • 上期有人问：能不能不等在电脑前把任务跑完。
  • 可实践的一层：一台配置拉高的主力机存全部文档；不方便开电脑时，用手机远程连上去下指令（微信文章丢给它做摘要、远程控制等）。
  • 许多产品都有类似能力，这一层相对好落地。

团队难在「偏好合不到一起」

  • 改文件、向量化、格式，除非沉淀成 Skill 或开源，每个人的审阅口味和规则都不一样，同一类错误要反复纠正。
  • 不同工具认的入口文件也不一样：有的认 AGENTS.md，有的认 CLAUDE.md。既要有项目级说明，也要有对所有项目生效的团队规范。

05分层记忆与项目复盘

三层怎么分

  • 通用层（AGENTS.md 一类）：权限、命名与存放、基础格式。所有项目先跑一遍这份指南。可更新，但是「宪法」，不要每聊一句就改。
  • 领域层：例如投资领域的概念／GAP，单独存放并同步。
  • 项目层：新项目结束让模型自动写复盘（人再口述改一版），指定目录分类存。基金新项目复盘覆盖旧规则也可以写进约定。

有人已做过多设备同步，但分层没写清，一开口上下文就暴涨。权宜之计：干活用子代理，子代理不把主对话的长上下文整段带下去。

别整本灌进窗口

  • 三份文档加起来会很长。写成「需要时再读」：目录在，章节按需打开，避免每次加载完整领域指南。
  • 项目积到十几二十个，全读会拖死效率。复用「过往类似项目」本身就不稳，同样的错还会再犯——这正是要做项目复盘的原因。

06团队文件怎么同步

规范文件：用仓库管

  • 三份 md 若人人可同时改，容易撞车。建议丢进 GitHub，改动走 PR，负责人批完再生效（现场比方：七个人有意见先汇到姚总）。
  • 云端 Agent 也常跟某个 Git 仓库绑定，规范放在仓库里，Agent 才能直接调用。

项目档案：本地挂载

  • 律师过往项目要归档。七个人各归各档很累；一人按编号分类归好，其他人同步到本地，AI 才能在过往项目里找类似参考。
  • 坚果云：本地文件夹 ↔ 云端，改完自动同步给同事；多账号、权限可拆（只能上传／不能下／不能改）。体感接近 Google Drive，比百度网盘好用（后者上传下载限制多、隐私口碑差）。
  • 多人同时在线编辑，坚果云也不是强项；「本地改完再同步」这条是成立的。

版本

  • Git／坚果云都能留历史，误删可回。Word／WPS 自己也有崩溃备份，和「规范仓库」不是同一层。
  • 有平台主打「很多 Agent 并行改同一份文件、并发高」；现场觉得律师日常很少碰到那种并发，招股书那种长文档另说。

07Skill 为什么没触发

姚总统计过约 40 个专用 Skill（法律文书、抬头、提取方法等），触发却很随机。现场排下来，不全是「关键词写得不够」。

盘符不在一层

  • Claude Code 装在 C 盘，项目在 D 盘。生成的定制 Skill 进了 C 盘 memory；跑项目时读的是 D 盘 memory，自然看不见。
  • 后来用链接把 D 盘 memory 指回 C 盘 Skill，好过一段时间；账号被封、改用中转后又复发。

中转把 settings.json 盖掉

  • 换 cc-switch 接国内模型后，每天开机该跑的 hook 整组消失。
  • Markdown 里仍写着「任务会自动触发」（软执行），真正的 hook 在 settings.json 里已经没了。
  • 原因：每次打开中转，会用旧版 settings.json 覆盖当前文件，用户级钩子被抹掉。
  • 处理：钩子改放到项目级配置。下次再换中转，就算用户级被盖，项目级还在。

没有版本对照就发现不了

  • Claude Code 自身不留这份配置的版本。另外给 settings 做 Git／定时快照，今天才能和昨天比「钩子掉没掉」。
  • Cursor 这类带 Git 的环境，这个问题轻很多。
  • 「再写一个 Agent 去盯 settings」会套娃：监控者本身也可能被覆盖。更稳的是把「跑项目前先核对钩子／机制是否还在」写进最高层说明文件。

08软约束要配硬检查

Markdown 只是软约束

  • 启动时会扫一遍说明，知道「今天要做 ABC」，但执行层不一定真的触发。它可能以为做了。
  • 工作目录越堆越满，注意力下降，写明「一定要做」的步骤也会被跳过。

两步就够用

  1. 精简装进大脑的东西：别当水桶灌满。只留一点点索引式记忆，其余放到按需读取的文档。
  2. 节点验收：例如生成的文档必须含某些章节；缺了就回头查数据、重做。流程里预留检查点。

孪生迁移：从 memory 到 harness

  • 原先 Skill 堆在 memory／长 Markdown 里，靠读触发词再去找，容易漏。
  • 把最常用的副本贴进 skills 文件夹。Claude Code 开工会强制扫这一层，斜杠命令（如催告函）才能出现。
  • Cursor 用户少这层困扰：自制 Skill 本来就在 harness，图形清单也好管理。
  • 40 个不必全搬。先搬每天真用的五六个；太散太细的合并。有人反过来认为：模型已经很强，新 Skill 加多了反而是束缚，该让它检测哪些约束是多余的。
  • 复合任务（调研 + 展开维度 + 落到 Word）常只召回其中一两条。综合性强的，用子代理，不要指望一条 Skill 包打。

09定制文书：催告函

姚总现场跑了催告函 Skill（已迁到 harness）。不清楚时按事先约定用选择题来问，例如是否已付款、用哪套标准推送。

  • 口吻按从前在君和写催告函的习惯；格式先生成再补章。不同律所的文风、态度差很多，这就是定制化的意义。
  • 连续两次输出大体稳定，仍取决于输入。正式用法：先丢整个项目文件夹让它读背景，再说清「这次真正要达到的态度」（要催到什么程度）。
  • 会扫工作区里旧函和模板。换工具难，是因为积淀已经绑在当前工作区。

有人在本机给 pandoc 做了右键／命令行快捷方式和一份备忘 reference，选中就能转 Word，体感很快。结论仍是：把路径收进 Skill 即可，不必执着于某一层快捷键。

10把工作抽象成工作流

诗总把原则收成一句：以前人是 first，现在可以 AI first——让模型主导流程，人参与关键判断。材料来自一份投研播客（后整理成书，链接此前已发群）。

投研框架里值得搬的

  • 工作先抽象：买数据源、按自己经验深挖、按汇报格式出稿。
  • 目录上能看到：灵感日报、大规模筛选、标的跟踪、每日财务监控、邮件汇报。
  • 信息先让模型读一遍，再给人看「他真正关心的那一小截」——人直接读模型长摘要容易胀。
  • 研究阶段接外部库、自建知识库、交叉验证，再出研报；跟踪用信号触发。

媒体知识库（B）

  • 对话里攒下来的信息会像水桶一样爆掉，爆了就什么都不记得。
  • B 只收最关键的抽象：一份财报到这里可能只剩几句话。它是索引，不是原文仓库。
  • 架构写在最高层说明里（如 CLAUDE.md），规定目录职责：原料进哪、简报进哪、模板进哪、知识库进哪。

工程目录 ≠ Skill 目录

  • 工程目录是用文件夹层级组织信息；模型知道「采集放 B、B 再汇总给人」。
  • 不一定非用终端。图形工作区按同一套浅目录管也可以，只是终端更顺手。
  • 给人读的：目录浅、好扫。给模型读的：分层清楚、体量大一些没关系。
  • 反馈是双向的：人要在节点上纠正规则。都是从小处调顺，再变复杂。

A 股数据有人用 WorkBuddy 免费用同花顺；海外数据源需另购。现场也聊到自建固定出口，结论是会后再单独请教，不在纪要展开。

11驾驶舱与任务分叉

列榜用 Codex 做产品（自述 ADHD，常 3–6 个项目并行）。最新例子是自助离婚：验证两件事——普通人愿不愿意为这类服务付费；没有律师坐镇时，Agent 能不能一步步陪到一份完备协议。需求量大、路径相对标准、输出主要是协议。

主对话只做驾驶舱

  • 开场先走「优化助手」：思路不完整也没关系，先展开成结构化需求，再开项目。
  • 驾驶舱写清：全流程、核心工作方式、当前状态；开工先审计、对齐理解，再动重活。
  • 有观点认为写代码不需要「长期记忆」——仓库和文件快照本身就是记忆。用权威文档记录已做决策、纪律、进度；换对话时读文件，而不是读被压过的摘要。
  • 系统自动压缩你选不了保真范围；handoff 时可以把纪律、决策日志完整留下，只压缩允许抽象的部分。

重活新开对话，结果回到主线

  • 调研、写代码、出专项报告，一律新开带编号的对话。开头提示词由驾驶舱写好，边界和要求一次性说清。
  • 和黑盒子代理的差别：过程可插话、可纠偏；做完经验收，再回主线。主线保持干净，支线都能规划。
  • Codex 交付后会把结论带回驾驶舱。尽调和起草交易文件可以并行，主线再命令对应分支改稿。
  • 同应用内的对话有 id，可以链过去复用（例如 A 项目已调研，B 项目只做补充）。跨应用读不了。

防漂移

  • 先画项目地图／主线，跑偏就审计、重新定位。提示词离当前窗口太远时，主动开新驾驶舱。
  • handoff 文档只给「要读的文件地址」，新窗口从断点续上。作用像快照：别等自动压缩已经偏了再救。
  • 经验阈值：标称窗口还没到自动压缩点，体感已经偏时（现场举例：大约 60k 就要醒，不要等到 80k）。检查太勤会慢，但关键节点必须看。
  • 律师友好的一点：结论要能回到出处（哪份文件、哪一段）。HTML 地图比两万行 Markdown 好扫，状态可更新，并行三条线时尤其有用。

技能迁移：Claude 被封后，可以让模型扫描现有 Skill，改写成目标工具的格式再装。别人仓库里的 Skill，description 带触发限定，批量改即可。把模型当聪明员工，需求说清比堆装饰更重要。

12多端同步与中文检索

启人在做「信息汇集中心」：微博、知识星球、新闻站订阅太吵，只想看白名单，而且全世界只留一个推送入口。

信息流

  • 网页源好办，知识星球已打通；各平台的抓取完整度不一，有的通道一天只能推一条，还没做到「全抓再筛」。
  • 通知层用 Bark 这类标准推送。爬虫和白名单接上之后，其他 App 通知可以关掉。

设备怎么跟 Agent 无缝

  • Mac／Windows／手机，OpenCode、Codex、WorkBuddy 并存时，文件同步很重。
  • 办法 A：规范与 memory 放 GitHub，其他端定时拉取（五到十分钟一档）。
  • 办法 B：公司虚拟机，所有东西放同一台，少一层同步（现场觉得最干净）。Mac Mini 当主力机也行，但要自己补远程入口，体验往往不如网页端「同一份服务器文件」。
  • 网页版 Agent：文件和对话在服务器上，电脑关了也是同一份；前端适配手机比例就能用。

选工具的取舍

  • WorkBuddy：不够开放，对话之间不能互访，权限死、很难让它改自己。
  • OpenCode：开源、开放，贵模型当主代理、DeepSeek 当子代理很好做；多端和生态要自己补。
  • Codex：自动化强，有持续开新对话直到做完并自验的模式。
  • 新出现的工作室可以把 Claude Code 和 Codex 收成下属资源来派活。
  • Fork 与子代理：从某一句复制出分支、带着到那一刻为止的上下文，和全新子对话不是一回事。有人觉得完整上文对账号被封、换模型续跑更友好。

中文搜索

  • 通用 Web Search 限量，且境内源偏少。
  • 权宜：让 Agent 打开浏览器去问元宝，再把页面结果收回来。不优雅，防抓也在加，但中文检索质量明显好一截。

13硬约束写作：国别白皮书

龚趴分享的是律师业务里的真实单：海外合规投资白皮书，客户预算大约传统价的十分之一（现场举例 2 万对 20 万），国别多、时间紧。Chatbot 无论提示词多长，输出仍是概率模型，Skill／脚本／MCP 也做不到硬约束，于是写成一套系统。

怎么跑

  1. 上传大纲模板（体例固定，国别可替换，如柬埔寨）。
  2. 解析大纲，把调研问题译成当地语言 + 英文，分别检索。杜绝中文语料。
  3. 检索用 Exa 的 answer 而不是 search：自己排序筛选走过弯路；answer 已筛过，再倒推信源、抓片段，做成事实卡（chunk）。
  4. 写作用 JSON Schema 骨架：只填框内，框外不能动。
  5. 每碰到句号／分号／问号／叹号，必须带 chunk id，句子和出处绑死。审阅只看卡片和原文（模型可附译文）。
  6. 质检两轮：DeepSeek 先严审（现场感觉九成以上是虚报），智谱再过。通过后导出 Word。

效率账

  • 测试：约 10 万字、137 个子节、700 余条脚注，11 小时 45 分，成本约 86 元。
  • 人工同类：快则一两周，细则一个月。体例、标题、行文在多本国别之间保持一致。
  • Exa 约 1000 次调用 5 美元。Perplexity 也可问，偏贵。JSON Schema 并非所有模型都支持得一样好。

「chunk」就是切出来的语料片段：宪法一千条不必整部进模型，只把相关段送进去。一致性主要靠骨架，不是靠更长的提示词。

14法律垂类产品实验

列榜团队在做 C 端和律所工具，用来验证「能不能把能力卖给别人」，不指望单品立刻赚钱。原则：还要培训才会用的产品，就是没做简单。

自助离婚（已上线试卖）

  • 中间是对话（可语音，图个陪伴感），已确认事实和待传资料分列。
  • 系统知道签这份协议还缺什么，在对话里要。场景短：沟通 → 收信息 → 定方案 → 对方确认 → 支付 → 导出协议。
  • 定价先试 699，高了再往 399。用来测转化，不是测能赚多少。

诉讼案件管理（给深圳一位市场型合伙人）

  • 组里十几人周一例会要开一两个小时，只为同步案子进展。
  • Agent 读新上传文书，能反映节点的那些排序后，推状态机；活动线看谁传了什么。
  • 法定期限从文书算（例如开庭通知送达后的举证期），避免「汇报过了第二天忘交诉讼费」。
  • 判断：能带来案源、或明显提高承办效率的，才值得做成产品；纯案件管理本身不值钱。

Legal OS（原型）

  • 仪表盘看当天待办；项目是卡片。左侧是典型工作流（如农资／投资项目）。
  • 过程与结果分开：调查事实的过程各所差不多；最后按各所模板组织报告（有的所先写基础事实再分析，有的所先把重大问题写在前面、事实做附件）。
  • 交互：左边结构化表（律师熟），右边补充对话，后台视为同一条需求。事实 → 分析 → 待证事实／待要文件，循环到 clear，再套模板导出。
  • 交易文件做版本对照；交割包上传后做义务勾稽。目标是从立项到 closing 像副驾，而不是一次性出全文。
  • 原子能力（找资料、调查、处理信息、写作）做基座，领域工作流再往上长。第一版只考虑个人：真实协作仍是 junior 写完交给 senior，人不在系统里合稿。

模型、定价、隐私（讨论未完）

  • 先用最强模型试一条链路，能跑再降到国内模型看 3–6 个月内能不能商用。卖给普通人时会接国内模型。
  • 积分 + 套餐比纯包月更接近背后的 token 结构；用量不均时更公平。本地化部署贵、模型迭代快，上门换模型会变成做不完的生意。
  • 隐私：邮件和微信传文件本来就在发生。去标识是悖论——行业、对价、时点去得太干净，模型做不了尽调；去不干净，人仍能猜出项目。
  • 收束时的问题还在桌上：通用 Agent 已经很强，垂类靠什么活？是任务质量，还是模型智能本身？法律工作大量仍是写作，深度研究（尤其国内案例）仍然难。
